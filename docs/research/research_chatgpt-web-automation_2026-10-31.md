# Own the ChatGPT page driver, borrow the logic

subllm should write its own small, page-side ChatGPT driver and port the hard-won logic from three MIT projects: **leeguooooo/image-use** for image generation, **steipete/oracle** for text (GPT Pro effort, Deep Research, completion and extraction), and **sologuy/chatgpt-web-handoff** as the reference for a plain-Python CDP adapter. Wrapping them as subprocesses does not work as the main path, because the one fact that fixes the architecture is that **ego lite exposes no CDP port and no SDK**. Its only agent interface is the `ego-browser nodejs` CLI, which runs JavaScript inside ego lite's own runtime. Oracle attaches to CDP endpoints and image-use is hard-wired to the chrome-use extension, so neither can drive ego lite. ego lite is installed on Kyle's Mac, so the preferred path must be subllm-owned code either way. The real choice is whether to run that same page script in the Chrome fallback too (one selector set to maintain), or to wrap oracle and image-use only on the fallback path (two selector sets against a UI that drifts every one to three weeks). This report recommends the single core. Several "allowed" candidates hide quota traps that would spend Codex/Work usage: image-use's default `auto` backend, TianLin0509's Codex lane, oracle's API engine, and ChatGPT's own new Work mode. The account risk is real but thinly evidenced. Driving the web UI breaches the Terms clause against "programmatically extract[ing] … Output". Yet the only firsthand bans on record hit replay pools of throwaway Free accounts, not a paid account driven through a real browser.

It stays unclassified ([architecture.md](https://github.com/miuuyy/codex-chatgpt-web/blob/HEAD/docs/architecture.md)).

The projects converge on technique, and that convergence is what subllm should port. For **images**, completion is "no Stop control AND a brand-new `<img>` in the current turn, stable across two reads". A missing Stop control alone is never terminal, because it may only mean a selector changed ([image-use SKILL.md](https://github.com/leeguooooo/image-use/blob/HEAD/skills/image-use/SKILL.md); [sologuy cgh_web.py](https://github.com/sologuy/chatgpt-web-handoff/blob/HEAD/bin/cgh_web.py)). Bytes come from an **in-page `fetch(src)`**, because redesigned accounts render results as same-origin `blob:` URLs that only the page can read. The search must be scoped to the current turn, because ChatGPT pushes an "Image created" toast with a thumbnail into every open chatgpt.com tab. Concurrency is one per account, since the page "rate-limits aggressively", and Temporary Chat disables image generation ([image-use SKILL.md](https://github.com/leeguooooo/image-use/blob/HEAD/skills/image-use/SKILL.md)). Aspect ratio goes into the prompt text, optionally followed by a crop. No project found a size control on the chat surface ([StaticB1 gen_asset.py](https://github.com/StaticB1/browser-llm-api/blob/HEAD/browser_llm/gen_asset.py)). For **text**, the pattern has five steps:

1. Select model and effort, verify the selection, and fail closed. Oracle's `pro` "abort[s] before submission if unconfirmed".
2. Complete only on a turn-scoped Copy button plus no composer-scoped Stop plus stable text.
3. Extract Markdown through the page's own Copy button, captured in-page.
4. Save the conversation URL at once.
5. Never resend.

([oracle browser-mode.md](https://github.com/steipete/oracle/blob/main/docs/browser-mode.md); [gpt-pro-relay](https://github.com/chrisliu298/gpt-pro-relay)). ChatGPT keeps generating server-side after the browser disconnects, so long Pro and Deep Research runs (5–40 minutes) can be reattached by URL ([yxhpy](https://github.com/yxhpy/chatgpt-pro-browser)).

This is the main argument for one selector set instead of two.

## ego lite runs as a subprocess, but Space login visibility is unproven

ego lite is a free, closed-binary Chromium fork from Citro Labs. It runs on macOS and Windows x64, with Linux "on the roadmap" ([citrolabs/ego-lite](https://github.com/citrolabs/ego-lite)). Its stated design is "no SDK to integrate, and no remote debugging to set up" ([lite.ego.app](https://lite.ego.app/)). The running app on Kyle's Mac has no `--remote-debugging-port` (local `pgrep`). The agent interface fits subllm's existing pattern of driving a CLI subprocess. Local probes against ego lite 0.6.2.5 (Chromium 156, embedded Node 24) established how it behaves:

- A script piped on stdin to `ego-browser nodejs` runs with the SDK globals (`taskSpace`, `listTaskSpaces`) pre-injected.
- **All console output arrives on stderr**; stdout was empty in every probe.
- An explicit `process.exit(n)` is preserved, and an uncaught throw exits 1.
- Scripts inherit neither the caller's environment nor its working directory.

The driver protocol follows from those probes. Python generates the script with inputs embedded as JSON literals and pipes it on stdin. The script prints exactly one `SUBLLM_RESULT <json>` line. Python treats the exit code as primary status and maps `EGO_TASK_SPACE_NAME_IN_USE` and `EGO_PAGE_UNRESPONSIVE` to typed errors. TaskSpaces and page labels persist across invocations while JS variables do not. A long Pro run can therefore be a short "send" invocation followed by "poll" invocations against a stable Space named `subllm-chatgpt`, closed with `task.finish({keep: []})`. `page.evaluate()` runs the shared page-side core, and `page.fetch(url, {saveAs})` saves image bytes with the page's own cookies (local guide v2.2.0). ego hides CDP console traffic from sites ("Page sessions hide page console messages from CDP so sites cannot detect the automation"). That is the most favourable posture available, but nothing measures it against Turnstile. The hosted docs still describe an older API (`useOrCreateTaskSpace`, `cliLog`) than the installed guide v2.2.0 ([ego-browser docs](https://lite.ego.app/document/en/docs/ego-browser)). The driver should therefore parse the guide-version banner, fail closed on an unknown major version, and never run `ego-browser upgrade` itself when `[ego-browser:notice]` appears.

**Detection, never assumption**, is a four-rung ladder:

1. `shutil.which("ego-browser")`, then `~/.local/bin/ego-browser`, where onboarding installs it off-PATH.
2. Parse `ego-browser --version`.
3. Parse the guide major from `ego-browser skill`.
4. A readiness probe: `ego-browser nodejs` must print a token within a short timeout. That is the vendor's own `ego-browser ready` check (local `references/install-macos.md`).

The vendor warns that `command -v ego-browser` alone "does not prove that commands run on the host computer" ([custom harness docs](https://lite.ego.app/document/en/docs/custom-agent-harness)). Fallback rules:

- `SUBLLM_CHATGPT_BROWSER=auto` takes ego lite when every rung passes, otherwise Chrome.
- An explicit `ego` setting fails closed instead of silently switching.
- Linux always uses Chrome.
- Nothing ever falls back after a prompt has been dispatched, because the answer may still land in the chat and a retry would spend Chat quota twice. image-use's `auto` mode encodes the same rule ([SKILL.md](https://github.com/leeguooooo/image-use/blob/HEAD/skills/image-use/SKILL.md)).
- Nothing ever falls back to Codex.

The open question is whether a Space sees Kyle's chatgpt.com login, and the vendor contradicts itself on it. The Space docs say both "One isolated BrowserContext per task, with its own cookies and storage" and that Spaces reuse "the login environment you already have" ([Space docs](https://lite.ego.app/document/en/docs/space)). The installed guide leans toward a shared jar. It warns that "Some clears reach the whole browser profile", it exposes `task.userPage()`, and it says a `profileId` applies only at Space creation (local guide v2.2.0). The resolution is a DOM-only probe that calls no internal endpoint, run once by Kyle:

1. In a `subllm-probe` Space, open chatgpt.com and report whether the composer or a "Log in" button is present.
2. If the Space is logged out, call `task.handOff()` so Kyle logs in inside the Space.
3. Finish, then open a second Space to test whether the login persists.

The outcome decides whether the driver needs a login hand-off flow, a fixed `profileId`, or nothing.

The **Chrome fallback** cannot attach to the default profile by relaunching with a flag. Since Chrome 136, `--remote-debugging-port` "will no longer be respected" on the default data directory ([Chrome blog](https://developer.chrome.com/blog/remote-debugging-port)). Chrome 144+ offers a consented attach, but it shows a per-session "Allow remote debugging?" dialog ([Chrome DevTools MCP blog](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session)). Copying profiles or cookies silently loses the session token, and oracle warns that cookie sync "can invalidate the user's Chrome session" ([oracle browser-mode.md](https://github.com/steipete/oracle/blob/main/docs/browser-mode.md)). The consensus substrate is real branded Chrome, headful, with a **subllm-owned `--user-data-dir`** and a one-time manual login. The best pip-installable launcher is [patchright](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-python) (Apache-2.0) `launch_persistent_context(channel="chrome", headless=False)`. It avoids `Runtime.enable` and the automation flags, and it runs the same page-side core through `page.evaluate`. chrome-use reaches the real main profile but needs an extension and a native-messaging host installed into the logged-in Chrome, which triggers Kyle's untrusted-install policy ([chrome-use](https://github.com/leeguooooo/chrome-use)). Cloudflare states that "automated browsers are not supported for solving production challenges" ([Cloudflare](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)). Both substrates must therefore treat a challenge as a hand-off to Kyle, never something to solve.

**Probe result (2026-10-31, ego lite guide v2.2.0).** Two agent task spaces opened at the same time share one cookie jar and `localStorage`: a cookie set on example.com in space A was visible in space B. Spaces therefore inherit the profile's logins, and the conflict in the docs resolves to "shared". Both spaces loaded chatgpt.com logged out (login button present, no profile button, no Cloudflare challenge), so the default ego lite profile simply has no chatgpt.com session yet. One manual login in ego lite is the fix. The driver's logged-in check plus `handOff()` covers expiry later.

After one manual login from a user tab (a Cloudflare "Verify you are human" Turnstile appeared on one load and was cleared by hand), two fresh agent spaces loaded chatgpt.com logged in. They showed the redesigned composer (`div.ProseMirror[role=textbox]`, `data-test-id` attributes present), no login button, and no challenge. The legacy `accounts-profile-button` test id was absent, so the logged-in check should use "composer present and no login button" rather than a profile-button selector.

## Browser driving still breaks one Terms clause

The consumer Terms of Use (effective 2026-01-01) prohibit, verbatim, "Automatically or programmatically extract data or Output". They also prohibit attempts to "circumvent any rate limits or restrictions or bypass any protective measures", and reverse engineering ([Terms of Use](https://openai.com/policies/terms-of-use/)). Nothing in the Terms exempts personal automation of the web UI. A browser driver on Kyle's own account therefore breaches the extraction clause. A replay client breaches all three. No official path exists for chatgpt.com-only features. Sanctioned subscription automation is limited to the Codex client and Sign in with ChatGPT, and both spend Work/Codex quota ([SIWC docs](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)). Two other things change on 2026-11-20. The Usage Policies revision adds the intermediary-approval clause, which hits gateways and not a local library used by its owner. It also prohibits "automation of high-stakes actions in sensitive areas without human review", which a summarizer does not touch ([Usage Policies](https://openai.com/policies/usage-policies/)).

**Enforcement evidence is lopsided.** Firsthand bans exist almost only for replay pools of bulk-registered Free accounts:

- Mass bans on 2026-06-15, with accounts that "只能活几小时" (live only a few hours) ([chatgpt2api #279](https://github.com/basketikun/chatgpt2api/issues/279)).
- A registration lock-down on 06-25 ([#313](https://github.com/basketikun/chatgpt2api/issues/313)).
- A 2026-10-14 risk-control wave that turned flagged accounts into `Model not found` even on the official web UI. One fork maintainer later said it was rolled back ([PR #418](https://github.com/basketikun/chatgpt2api/pull/418)).

The researchers found no firsthand report tying a ban to Playwright or CDP driving chatgpt.com on a paid account. The nearest data point is Cloudflare blocking, not banning ([Latenode thread](https://community.latenode.com/t/playwright-automation-getting-blocked-by-cloudflare-when-accessing-chatgpt/21831)). Absence of reports is not safety. An 18-month Pro subscriber who denies any scripting was banned with a generic "Terms and Usage Policies" notice and suspects a shared data-centre egress IP ([OpenAI Community](https://community.openai.com/t/codex-chatgpt-pro-account-banned-with-no-warning-no-explanation-18-month-subscriber/1381906)). Detection also goes beyond the network. Reverse engineering shows Turnstile reads hydrated React state, and a "Signal Orchestrator" records keystroke and pointer timing ([Buchodi](https://www.buchodi.com/chatgpt-wont-let-you-type-until-cloudflare-reads-your-react-state-i-decrypted-the-program-that-does-it/)). A real browser passes the first by construction. Nobody has measured what synthetic input costs on the second. The practical rules follow: run only from residential egress (never VPN or WARP), keep one account at personal volume and concurrency one, and hand off every challenge.

**The GPT-6 Pro cap is the binding text constraint, and the numbers are unconfirmed.** Search snippets of help-center pages (fetches returned HTTP 403) give **200 GPT-6 Pro messages per week in Chat on Pro $200** and **50 per week on Pro $100**, the latter shared with GPT-5.6 Sol Pro. On exhaustion, Pro falls back to **GPT-5.6 Thinking (Medium)**. The same source says GPT-6 Pro is available in Chat on Pro $100, Pro $200, Business and Enterprise, and is "not included with ChatGPT Plus in standard Chat" ([OpenAI Help 20001354](https://help.openai.com/en/articles/20001354)). On Plus, the text backend loses its main advantage over `codex exec`. That silent downgrade means a selected Pro label proves nothing. Oracle itself calls its recorded selection "UI evidence, not proof of backend effort". gpt-pro-relay adds a post-completion served-model audit that writes `response.rejected.md` on mismatch ([oracle browser-mode.md](https://github.com/steipete/oracle/blob/main/docs/browser-mode.md); [gpt-pro-relay](https://github.com/chrisliu298/gpt-pro-relay)). The driver needs both a pre-send fail-closed check and a post-hoc audit. It should also reject "Thinking failed" turns, seen on GPT-6 Pro around 2026-09-24 ([community thread](https://community.openai.com/t/thinking-failed-in-chatgpt-pro-6-astra-on-chatgpt/1400485)). One premise remains untested. Pro mode is web-only, since the Codex models page lists no Pro tier ([Codex models](https://learn.chatgpt.com/docs/models)), but **no benchmark shows web Pro beating Codex `gpt-6-astra` at Max/Ultra**.

## Recommendation: one page-side core, two thin substrates

**Image: port from image-use. Text: port from oracle.** Use sologuy as the template for a plain-Python CDP adapter, and treat Zeno-Zhu's redesign commit and TianLin0509's `p=fs` original as selector and retrieval references. All are MIT, so vendored snippets need only attribution. gpt-pro-relay has no license and contributes design ideas only. Do not depend on any gateway-shaped project.

The architecture has one JavaScript module of pure page functions, `page_core.js`, and two thin substrate drivers behind one `BrowserDriver` protocol:

| Part | Responsibility |
|---|---|
| `page_core.js` | Logged-in check; Chat-not-Work check; model/effort select and verify (fail closed); composer fill and single send; turn-scoped completion; Copy-button capture; current-turn image detection and in-page `fetch` to base64. Matches both the legacy and redesigned DOM, with fixture tests for each. |
